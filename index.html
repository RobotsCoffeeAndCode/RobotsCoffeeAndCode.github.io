Software Engineering & Design

I anticipated that this initial enhancement would be substantial, but I did not expect it to require so much time. This oversight was primarily due to the effort I invested in making the project conform to industry-standard software engineering practices. In retrospect, I made the challenging decision to move beyond the tools I was familiar with, Visual Studio and MSVC (Microsoft’s C compiler), and adopt another compiler widely recognized in the industry: LLVM's Clang. This is not to say that MSVC compiler or Visual Studio is a bad IDE choice, but I wanted to leverage the efficiency optimizations that come with clang for future work.

I made this choice for several key reasons. First, I aspire to become an embedded systems engineer, a role that requires a strong foundation in C and C++. Developing that foundation involves working more closely with the compiler and tools such as Makefiles and CMake. Second, Clang includes a range of built-in tools. For example, I use clang-tidy, a static analysis tool included with Clang, to improve the security of my code. Finally, using Clang with CMake offers flexibility: including a CMake build file in a project allows tools to be added to the build toolchain as needed. For instance, I run a simple Google Test suite as the final step in my build process to verify that my unit tests pass before testing runtime features.

These considerations led me to try Clang and adopt a less structured, yet organizationally demanding project setup. After installing and configuring everything, learning how to compile the project correctly, encountering repeated failures, and reimplementing Google Test, I was able to get a small piece of C++ code working properly.

After writing C++ code using clang-tidy and clangd (Clang's built-in Language Server Protocol, or LSP), I realized that I had significant room for improvement in my C++ programming. For example, I was unaware that a modern style convention is to begin a function definition with the keyword `auto` and specify the return type afterward. I was also unfamiliar with the chrono library, as I rarely have worked with calandar dates. However, as my project made heavy use of them I used the `year_month_day` object frequently. This proved to be extremely useful for tracking rescue animal date data. I also had to become accustomed to clangd’s formatting conventions. Initially, it was difficult to read my function parameters because I usually place each parameter on a separate line, whereas clangd prioritizes an 80-column line width. I eventually learned how to configure it to enforce line-by-line parameters, but by then I was nearly finished with the second enhancement. Algorithms & Data Structures

This second enhancement deepened my understanding of graph algorithms, efficient graph representation in code, and the importance of data encoding. My objective was to implement functionality for relocating a service animal, together with an estimated cost for the work. At a high level, I aimed to create a graph data structure that simulates flight connections between continents and assigns an estimated cost based on the actual distance in miles. Understanding the different ways to represent this graph (matrix versus adjacency list) and developing a straightforward estimation system were the least challenging parts of this enhancement. I created an adjacency-list representation to minimize memory usage and used the distances between the geographic centers of each continent, multiplied by the average cost per mile of air travel ($0.18 at the time of research), to create a graph that could be searched.

The next, more challenging step was determining which algorithm to implement and why. My initial choice was Dijkstra’s algorithm, since there were no negative edge costs and, given how simplified the graph was, developing a realistic heuristic for A* did not seem reasonable. Knowing that my initial intuition often needs refining through research, I started to study the algorithms commonly used in satellite navigation. This is primarily because I viewed this problem as a more complex extension of my own, that already has an excellent solution. It appears that much of the work on algorithms foundational to satellite navigation focuses on contracting the enormous graph of path data already available. Consequently, the tradeoff involved in implementing any of these improvements did not seem worthwhile for my simple graph. The only useful addition I found was the bidirectional version of Dijkstra’s algorithm, which reduces search time by running Dijkstra’s algorithm from both the start and target nodes. However, after considering its implementation complexity, I concluded that the time investment was not justified by the modest efficiency gain. Returning to my original approach, I implemented Dijkstra’s algorithm.

The final and most challenging part of implementing this enhancement was adapting the members of my existing RescueAnimal class to work with the newly created graph. I chose to use continents rather than countries (I believe the number of connections between countries is upward of 15,000) and encode them alphabetically, from zero to six. As a result, I had to rename many functions, create helper functions to encode a string as its corresponding size_t value, and add checks to prevent access when inServiceContinent, which I chose to make a C++ optional type, is nullopt. The creation of the graph and implementation of the algorithm proceeded smoothly. However, the encoding work, along with renaming half of my functions from country to continent, was a large time sink.

// Holds shortest paths, predecessor tracks, and the source vertex
struct DijkstraResult {
  static constexpr int infinity = std::numeric_limits::max();
  static constexpr std::size_t kInvalidVertex = std::numeric_limits::max();

  std::vector distances;
  std::vector predecessors;
  std::size_t source{0};

  // Reconstructs the shortest path sequence from source to target
  [[nodiscard]] std::optional>
  getPathTo(std::size_t target) const;
};

and this is my implementation of Dijkstra's

        
// Implementation of Dijkstra's Algorithm, takes a graph and source vertex
// returns a DijkstraResult with costs to navigate to other nodes from source
DijkstraResult dijkstra(const ContinentGraph &graph, std::size_t startVertex) {
  const std::size_t vertexCount = graph.getVertexCount();
  if (startVertex >= vertexCount) {
    throw std::out_of_range("Start vertex index out of bounds.");
  }

  std::vector distances(vertexCount, DijkstraResult::infinity);
  std::vector predecessors(vertexCount, DijkstraResult::kInvalidVertex);

  // Min-heap ordered by smallest distance first
  std::priority_queue, std::greater> prioq;

  distances[startVertex] = 0;
  prioq.push(QueueNode{.distance = 0, .vertex = startVertex});

  while (!prioq.empty()) {
    const auto [currentDist, u] = prioq.top();
    prioq.pop();

    // Skip processing if a shorter path to u has already been finalized
    if (currentDist > distances[u]) {
      continue;
    }

    for (const Edge &edge : graph.getNeighbors(u)) {
      if (edge.weight < 0) {
        throw std::invalid_argument("Dijkstra does not support negative weights.");
      }

      // Safe relaxation check preventing signed integer overflow
      if (distances[u] != DijkstraResult::infinity &&
          distances[u] + edge.weight < distances[edge.to]) {
        distances[edge.to] = distances[u] + edge.weight;
        predecessors[edge.to] = u;
        prioq.push(QueueNode{.distance = distances[edge.to], .vertex = edge.to});
      }
    }
  }

  return DijkstraResult{.distances = std::move(distances),
                        .predecessors = std::move(predecessors),
                        .source = startVertex};
}

Database Integration

As with my previous enhancements, I significantly underestimated the scope of this work. I initially thought that Supabase offered a native C++ integration and that my life was going to be a bit easier. Yet upon scouring their documentation, I failed to find any. As a result, I relied on two additional third-party libraries to create a client for making HTTP requests to the Supabase API. The first, nlohmann, is a header-only library that provides a C++ JSON class. I used this class to parse JSON responses and construct payloads for sending to the API when retrieving or saving local instances of user data. The second, CPR (C++ Requests), is a library built on cURL and libcurl that provides a simplified interface for making basic HTTP requests, among other capabilities. This was its primary use in my project.

In addition to implementing this HTTP client, I created a basic login screen and a test user account with pre-populated data. I removed the initializeDog() and initializeMonkey() functions from main.cpp, as all seeded data is now stored in this account. When the application opens, users are prompted to sign in or create an account. Users are welcome to create their own accounts to explore the application. Usernames must be in email format, although they do not need to correspond to valid email addresses because email verification has been disabled for the purposes of this project. To access the test account, use “admin” as the email and “test” as the password. Any changes made to the animals associated with the test account will persist in the database. This can be verified by closing the application and signing in again.

In addition to integration of the database functionality, I refactored a substantial portion of the code. I had repeatedly violated the DRY (Don’t Repeat Yourself) principle in the previous enhancement, so I worked to address this issue. Along with removing duplicated logic, I simplified several functions in main.cpp in response to feedback from clang-tidy. In particular, I divided reserveAnimal() into three smaller functions, separating its original responsibilities into more manageable parts. I then gave the same treatment to my printAnimals() function, splitting how it handles filters from the actual printing to stdout. I also consolidated several enum and encoded representations. Specifically, RescueUtils.hpp now contains only the continent graph encoding, alongside the sole representation of valid monkey species.

Conclusion & Future Work

Looking back on this experience, transforming a basic first-term Java console program into a modern C++ application has served as a tangible representation of my growth at SNHU. When I initially wrote the IT-145 project, my understanding of software engineering was mostly functional and confined to immediate syntax. Re-designing this project in C++ forced me to confront foundational software engineering paradigms: enforcing security best practices through strong typing and modern libraries (`std::chrono`, `std::optional`), establishing polymorphic abstractions to avoid dynamic runtime casts, and implementing rigorous static analysis via clang-tidy. This project helped me bridge the gap between merely writing code that runs and architecting maintainable, secure systems.

The primary constraint across this project was the rigid six-week development timeline (eight-weeks for the full course) dictated by the CS-499 course format. Allocating essentially two weeks per enhancement created significant pressure to prioritize core architectural functionality over non-essential features. In Enhancement 1, understanding the Clang toolchain, CMake configurations, and Google Test integration consumed far more setup time than anticipated. Similarly, discovering the lack of a native C++ Supabase SDK in Enhancement 3 required rapidly researching, integrating, and statically linking third-party libraries (CPR and nlohmann/json). Operating under this constraint simulated a fast-paced development sprint, teaching me how to make pragmatic engineering trade-offs. For instance, opting for the standard Dijkstra's algorithm over its bidirectional version when the graph size did not justify the implementation effort.

With all of these experiences and constraints from progressing through the project stated, there are a few things that I felt I could improve if I had more development time.

  • Delete functionality: I haven't fully implemented a CRUD application. I think that what I have demonstrated shows that I understand how to interact with a database and that I could confidently add this feature to my supabase client. Yet, as of writing this I have not fully implemented the ability to delete an animal from the database. Should I return to this project, this would be my first priority.
  • Moving from Console App to GUI Interface: As all of the core functionaltiy, besides what is mentioned here, has been implemented. I think a fair extension would be to add a more appealing user interface. The addition of a library such as Qt or Dear ImGui would make this software worth actually distributing to a small group of users for testing.
  • Testing: While I implemented a test suite and wrote some simple tests, I failed to provide even near the level of test coverage that a professional application would have. Because there are only a few library integrations within this application it really should have all branches of its execution unit tested and a overall coverage metric calculated.
  • Direct Career Goal Alignment: I really enjoyed this project because I have been able to showcase a wide range of computer science skills and the ability to work with modern collaborative tooling. However, my goal is to become an embedded systems engineer and many of these skills are less relevant to this specific role. If I had more time the addition of some role-specific skills would've benefitted me and this projects quality tremendously. Yet, in hindsight, this project has allowed me to display all of the skills I have beyond my chosen industry specialization. Even this very website is a skill that is not usually shown to employers when applying for the role and I am thankful that I have an active record of the breadth of my skills.

Ultimately, this capstone demonstrated that software engineering is fundamentally about managing complexity and trade-offs. Transitioning from high-level Java to low-level C++ with industry-standard build systems gave me the hands-on architectural experience, discipline, and tooling literacy needed as I transition into the professional software engineering landscape.
